# MULTI_POLICY_COMPLETENESS_REPORT

This audit analyzes the current implementation status of the Multi-Policy Architecture (One Lead → Multiple Policies → One Email → One Combined Intake Form) across the complete data lifecycle.

---

### SECTION A: Completed Functionality

**1. Lead Creation UI** (`app/(dashboard)/*/leads/new/page.tsx`)
- **Uses temp_leads_basics?** Yes (assigns `policy_type = primaryPolicy` as a fallback).
- **Uses lead_policies?** Yes (batches all selected policies into the secondary table).
- **Multi-Policy Compatible?** Yes. The user can select multiple policies via the new `MultiSelectPolicy` component.

**2. Lead Storage (Database)**
- **Uses temp_leads_basics?** Yes.
- **Uses lead_policies?** Yes.
- **Multi-Policy Compatible?** Yes. Data structures correctly represent a 1-to-many relationship.

**3. Intake Form Rendering** (`app/intake/[id]/page.tsx`)
- **Uses temp_leads_basics?** Yes (via `temp_intake_forms.form_type` string).
- **Uses lead_policies?** Yes. The component actively executes a database query to `lead_policies` to calculate the `activePolicies` array.
- **Multi-Policy Compatible?** Yes. It dynamically renders combined forms (e.g., `<HomeInsuranceForm />` + `<AutoInsuranceForm />`) on the same page based on the array.

---

### SECTION B: Partially Completed Functionality

**4. Preview Form Link Generation**
- **Uses temp_leads_basics?** N/A.
- **Uses lead_policies?** Indirectly (by opening the Intake page).
- **Multi-Policy Compatible?** Partially. The URL syntax currently generated by the frontend still appends single-policy query parameters (e.g., `?type=auto`), but the destination `intake/[id]` page intelligently overrides this by checking the `lead_policies` table.

---

### SECTION C: Still Using Legacy Single-Policy Logic

**5. Send Email Modal** (`app/(dashboard)/csr/pipeline/personal/send-form/page.tsx`)
- **Uses temp_leads_basics?** Yes (Selects singular `policy_type`).
- **Uses lead_policies?** **NO**. Completely ignores the table.
- **Multi-Policy Compatible?** **Completely Broken**. 
  - The UI hardcodes `const [formType, setFormType] = useState('home')`.
  - It restricts the view to a single dropdown selection.
  - It forces rendering labels like `AUTO INSURANCE / AUTO` instead of representing the composite lead.

**6. Form & Email Templates Data Fetching** (`EmailGenerator`, `app/api/send-email/route.ts`)
- **Uses temp_leads_basics?** Yes.
- **Uses lead_policies?** **NO**.
- **Multi-Policy Compatible?** **Completely Broken**.
  - `email_templates` are explicitly fetched using `.eq('policy_type', formType)` where `formType` is a single string.
  - The API does not have logic to fetch or combine multiple templates (e.g., sending the Home Onboarding Template AND the Auto Onboarding Template in one email).

### SECTION E: Remaining Implementation Work Required

To fully satisfy **"One Lead → Multiple Policies → One Email → One Combined Intake Form"**, the following architectural changes must be implemented:

1. **Refactor Send Email State Management:** 
   The `send-form` page must query the `lead_policies` table on mount to calculate an array of `activePolicies`. The rigid single-string `formType` state must be upgraded to support array-based logic or a "Multi-Policy" aggregate state.
   
2. **Dynamic Template Composition:**
   The `email_templates` database querying logic must be overhauled. If a lead has Home + Auto, the system must either:
   - Allow the user to select a dedicated "Home + Auto Combo" template.
   - Automatically fetch both the "Home" and "Auto" baseline templates and concatenate their bodies (`finalBody = homeTemplate.body + '<hr>' + autoTemplate.body`).
   
3. **Intake ID Generation Logic:**
   The `ensureIntakeForm()` function currently maps a lead to a single string `form_type` in `temp_intake_forms`. This restricts email linkage. It should be modified to register the Intake session as a `combo` or `multi` type, or intelligently track the associated array of policies.
